# Resource: honeycombio_telemetry_schema

Manages the custom telemetry schema of your Team: a [Weaver](https://github.com/open-telemetry/weaver) registry document, written as YAML, which describes the telemetry your services send.

-> This resource requires the provider be configured with a Management Key with `telemetry-schema:read` and `telemetry-schema:write` in the configured scopes.

~> **Warning** A Team has exactly one telemetry schema, shared by all of its Environments and Datasets.
Creating this resource fails if the Team already has a telemetry schema, and leaves that schema in place.
To manage a schema which already exists, [import it](#import) first.
Two of these resources which manage the same Team, including ones in separate configurations or workspaces which point at different Environments, overwrite each other's schema whenever either is updated.
Manage the schema from one resource only.

~> **Warning** Who can write the schema is controlled by who can create a Management Key with the `telemetry-schema:write` scope.
Anyone who holds such a key can replace or delete the Team's schema outside of Terraform.
Restrict who can create those keys.

-> After an apply, agents which use the schema may keep seeing the previous version for up to 2 minutes, because the schema is cached.

## Example Usage

```terraform
resource "honeycombio_telemetry_schema" "example" {
  # Read the schema from a file so that it is sent exactly as written.
  schema_yaml = file("${path.module}/telemetry-schema.yaml")
}
```

## Schema

### Required

- `schema_yaml` (String) The telemetry schema, as the YAML of a [Weaver](https://github.com/open-telemetry/weaver) registry, of up to 1 MiB (1,048,576 bytes). It is stored and returned exactly as written, so any change to the text, including whitespace and comments, is a change to the schema.

### Read-Only

- `id` (String) The slug of the Team the schema belongs to.

## Schema Text

The schema is stored and returned exactly as written. The provider does not parse, format or normalise it.
Any difference between the stored text and your configuration, including whitespace and comments, appears as a change in the plan.

Use the `file` function, as shown above, to avoid unintended changes to the text.
Be careful with [heredocs](https://developer.hashicorp.com/terraform/language/expressions/strings#heredoc-strings): `<<-` removes leading indentation and a heredoc always ends with a newline.

The schema must be a valid Weaver registry. If it is not, the apply fails with the error from Honeycomb.

## Import

A Team's existing telemetry schema can be imported by the slug of the Team. The slug is the first part of the path in Honeycomb URLs, such as `ui.honeycomb.io/my-team/environments/production`, and the `team.slug` attribute of the `honeycombio_auth_metadata` data source.

To bring an existing schema under management:

1. Add a `honeycombio_telemetry_schema` resource with `schema_yaml` set to the schema you want.
1. Import the existing schema. e.g.

```
$ terraform import honeycombio_telemetry_schema.example my-team
```

Or with an [`import` block](https://developer.hashicorp.com/terraform/language/import):

```terraform
import {
  to = honeycombio_telemetry_schema.example
  id = "my-team"
}
```

1. Run `terraform plan`. The plan shows how the existing schema differs from your configuration. There is no change if they match exactly.
1. Run `terraform apply` to replace the existing schema with the configuration, or change the configuration to match the existing schema first.

The slug must be that of the Team of the provider's Management Key. Importing any other slug fails.
